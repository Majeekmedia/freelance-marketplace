# Deployment — Trust-Prime

Derived from `hosting-capability.md`. Never assume root access, a process manager
or a binary that has not been confirmed on the host.

## Target

- Hosting type: **shared cPanel**
- Web server: **Apache 2.4**
- Document root: **`public/`**
- PHP: **8.3** on host
- Deploy method: upload over restricted SSH, or cPanel File Manager

## Environment configuration (get these right or links break)

| Key | Production value | Why it matters |
|---|---|---|
| `APP_ENV` | `production` | disables debug pages and verbose errors |
| `APP_DEBUG` | `false` | **a stack trace in production leaks file paths and SQL** |
| `APP_KEY` | generated once on the server | encrypts sessions and encrypted columns |
| **`APP_URL`** | `https://your-real-domain.com` | **every absolute URL is built from this** |
| `SESSION_SECURE_COOKIE` | `true` | cookie must not travel over plain HTTP |
| `SESSION_DRIVER` | `database` | shared hosts behave oddly with file sessions |
| `QUEUE_CONNECTION` | `database` | no worker daemon available |
| `CACHE_STORE` | `database` | Redis not assumed |

### Why `APP_URL` is not merely cosmetic

It is the base for **every URL the application generates**:

```
route('password.reset', [...])   → https://APP_URL/reset-password/{token}
URL::signedRoute('file.download') → https://APP_URL/...?signature=...
asset('build/app.css')            → https://APP_URL/build/app.css
```

The dangerous case is **queued email**. A password reset link is generated by a
cron worker, not by a browser request — there is no request to infer a host from,
so `APP_URL` is the *only* source of truth. A wrong value emails reset links to
the wrong domain, which looks like a phishing attempt and is unusable.

**Observed, not assumed** — generated from CLI on 2026-11-20 with the default
value in place:

```
RESET LINK: http://localhost/reset-password/3a8ac63c…?email=browser%40example.test
```

If that email reached a real user, the link would be dead on arrival.

> Set `APP_URL` to the exact production origin — scheme included, no trailing
> slash — **before the first deployment**, and verify by triggering a real
> password reset on the live host and reading the received email.


## Build

- `npm run build` runs **locally** — Node is not assumed on the host.
- Upload `public/build` with the release.
- `.env` lives **outside** `public/`, at the application root.
- Minimum env: `APP_ENV=production`, `APP_DEBUG=false`,
  `SESSION_SECURE_COOKIE=true`, `SESSION_DRIVER=database`, `QUEUE_CONNECTION=database`,
  `CACHE_STORE=database`.

## Cron entries (both required)

```
* * * * * cd /path/to/app && php artisan schedule:run >> /dev/null 2>&1
* * * * * cd /path/to/app && php artisan queue:work --stop-when-empty --max-time=50 >> /dev/null 2>&1
```

Without the second, **no email is ever sent** — the queue silently fills.

## Migrations

- Run by the developer over restricted SSH.
- **Backup taken and verified before every migrate.**
- Never run `migrate:fresh` or `db:wipe` against production.
- Destructive migrations (drop/rename column) require written approval and a
  forward-fix plan, because a code rollback does not undo schema.

## Storage

### What `storage:link` actually does

Laravel splits file storage into two places on purpose:

```
storage/app/            ← NOT web-accessible (safe for private files)
storage/app/public/     ← meant to be public, but is still outside the web root
public/                 ← the only directory Apache serves
```

`php artisan storage:link` creates **one symlink**:

```
public/storage  ──▶  storage/app/public
```

That is the entire command. It creates no files, copies nothing, changes no
permissions. It makes `public/storage/...` resolve to the same inode as
`storage/app/public/...`, so a file saved to `storage/app/public/brand/logo.png`
becomes reachable at `https://site.com/storage/brand/logo.png`.

On this machine it is a Windows **junction** (verified 2026-11-20), which is the
Windows equivalent of a symlink.

### Why it can fail on shared cPanel

| Cause | Symptom | Workaround |
|---|---|---|
| Symlinks disabled by host policy | `symlink(): Operation not permitted` | serve files through a controller route |
| `open_basedir` restriction | link exists but requests 403 | same |
| Deploy via ZIP/FTP | link silently missing after upload | re-run `storage:link` over SSH or a one-off route |
| Files written to `public/` by mistake | works locally, 404s in production | never write to `public/` directly |
| `storage/` permissions | 403 even with a valid link | `chmod -R 775 storage bootstrap/cache` |

### What breaks here if it fails

| Feature | Uses the link | Impact if broken |
|---|---|---|
| **Brand logo** (FR-035) | yes | logo missing; the **text wordmark fallback still renders**, so the site looks almost correct — the most deceptive failure mode |
| **Portfolio images** (FR-008) | yes | broken images on freelancer profiles |
| **KYC documents** (FR-020) | **no — by design** | live in `storage/app/private/`, served only through an authorised controller |
| **Deposit proofs** (FR-039) | **no — by design** | same |

> KYC and deposit files are deliberately **not** in `storage/app/public`. They are
> identity documents and financial evidence; a guessable URL must never be enough
> to read them. Controller-served is not a workaround there, it is the design.

### The fallback when the link is unavailable

Public assets that would have used the symlink get a controller route instead:

```
GET /media/brand/{file}    → streams storage/app/public/brand/{file}
GET /media/portfolio/{id}  → authorises, then streams
```

One PHP process per image instead of letting Apache serve it directly —
acceptable for a logo and portfolio thumbnails, and far better than a broken site.

**T-030 verification:** confirm the link exists, then load a page rendering an
uploaded logo and confirm the image returns 200, not 404. A 404 here is invisible
on a page that also has a wordmark fallback, so it must be checked explicitly.

## Smoke tests after every deploy

| # | Test | Expected |
|---|---|---|
| 1 | Home page | 200, funded jobs visible |
| 2 | Registration | creates a pending account |
| 3 | Login as admin | dashboard loads |
| 4 | Unfunded job URL | 404 |
| 5 | `/admin` as poster | denied |
| 6 | Queue drained | a test email arrives |
| 7 | Logs | no new errors |

A deploy that "worked" but filled the log with errors is a failed deploy.

## Rollback

- **Code:** restore the previous release directory.
- **Database:** a code rollback does **not** undo migrations. Ship a forward fix or a
  tested reverse migration — never improvise on production.
- **Files:** uploads live outside the release directory so they survive a code
  rollback; confirm this before the first deploy.
- **External effects:** approved deposits and paid withdrawals cannot be un-sent —
  compensating entries only.

## Maintenance

- Dependency review: monthly (`composer outdated`, `npm audit`).
- Backup + **tested restore**: weekly, with the date recorded.
- Log review: weekly.
- Ledger reconciliation: monthly — total credits must equal total approved deposits.
- Access review: quarterly — who still needs admin?
